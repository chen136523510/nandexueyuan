### BUG-107 二修：真根因=「起立」配方无离位位移（锚点编排有 standExit、直调配方没有）

- **实证**：院长终态图=诺诺站在床垫上（图1）/站在椅子座面里腿穿座面踩底盘（图2）。白机复现：坐下→点配方 HUD「起立」→ root 原地不动 [1.05,-3.25]，roomCheck 爆 8 条（双脚踩椅盘 pen 0.22m/小腿穿椅座/手穿椅背）——与院长图完全一致
- **根因**：离位滑步（standExit）只挂在 `goToAnchor` 锚点编排里；**任何直接调用 stand_up 配方的入口（配方 HUD/未来大脑工具调用）都没有位移**——起立配方只管骨骼、root 位移是 roomApi 的事，两者割裂
- **修复**：`playRecipe` 播放入口统一挂钩——检测 `rc.id==='stand_up'` 且 sitAnchorKey 非空时，取该坐姿锚点的 standExit **自动 moveTo 离位**（清 sitAnchorKey 前先取值）；`goToAnchor` 里的重复 moveTo 同步删除（避免双滑步）。**架构含义：起立语义=「从座位上起来站到座位旁」，位移属于语义的一部分**，任何调用方都自动获得
- **验收**：椅坐→HUD 起立→[1.05,-2.72] 椎南站点 check 空；床坐→起立→[3.50,-2.72] check 空；锚点编排回归正常
- **教训**：**"语义完整性"要放在统一入口保证**（配方=骨骼、位移=场景 API 的两套系统必须有语义级粘合点）；首轮流检结论"旧构建"是错的——不是院长缓存问题，是我没覆盖到他用的入口

### BUG-108 二修：v5「手压大腿」实测穿腿→回退垂手微前位（v6）

- **实证**：床坐特写=手掌网格整个嵌进大腿根（腕骨点距腿轴 67~70mm"达标"，但手掌从腕部继续下垂、掌体在腿面下方）；上臂 x 抬到 -38°+hand x ±40° 扭转均救不回（腕骨 y 0.519 仍低于大腿表面 ~0.57）
- **根因**：①**骨点距离≠网格不穿**——手掌是有体积的（掌+抱拳指），"点贴面"验收是必要非充分条件；②压腿落点对坐姿敏感（椅/床髋高差 9cm，同一组角度在床坐下嵌更深）
- **修复**：撤 v5 压腿组，改**垂手微前微外**（上臂 x 前抬 10°+z 微外展 4°）——手自然垂在大腿旁外侧，距腿轴 **113mm**（净空 ~30mm+），不依赖腿面精确高度、双坐姿通用
- **验收**：床坐/椅坐特写+全景，手在腿旁清晰分离、roomCheck 零违例（`bug108_bed_sit_v6_droop_20261009.png`）
- **教训**：**「贴面放置」类姿势必须以网格体为验收单位（截图目检）**，骨点距离只是初筛

### BUG-106 三轮定版：比对真人手参照重调（v2 过度矫正+拇指方向错误）

- **院长指令**："手部依旧有问题，你最好是去看看具体人的手，尤其是女孩子的手来做比对"
- **真人参照（联网比对）**：放松手解剖域=MCP 屈曲 20~40°/PIP 30~50°/DIP 10~25°（小指侧略多、指尖阶梯排列）；拇指自然内收、指尖对食指/中指侧而非贴掌心——**v1 恰在域内偏松（"半摊手"观感），v2(55/60/38) 全维超域=用力握拳非放松**
- **拇指关键发现（off 通道数值扫描实证）**：对 leftThumbProximal 三轴 ±40° 扫描（拇指端↔食指中节距离）——**y 轴（内收）是唯一主驱动**（y+40 最优 49mm）；而 `THUMB_TWIST` 绕 x 正向实为**外张**方向，v2 的 twist 35° 与 y 内收 30° 互相打架，净效果=拇指翘在外面——这正是"手型依旧有问题"的主因之一
- **定版 v3**：四指取域上沿 Index 35/45/20 · Middle 38/48/22 · Ring 40/50/23 · Little 42/52/25（单指合计 100~119°，蜷而不握）；**Thumb Proximal 内收 45°、THUMB_TWIST=0**（特写验收：拇指收拢贴食指侧、四指并拢微蜷，`bug106_hand_v3_thumb_20261009.png`）
- **教训**：①参数域要有**外部参照**（解剖学/真人照片），不能在"上一版±几度"里盲调——v1→v2 就是在无参照下过度矫正；②实验必须走**可持续生效的通道**（off），直接改 node.quaternion 会被 apply() 每帧覆盖（两轮无效实验的根因）；③拇指这类"方向敏感"关节先做**轴向扫描**再定参数，不猜



### BUG-106 四轮：掌心朝向修复 + 解剖结构化精细建模（v4，院长三轮反馈）

- **发现时间**：2026-10-09（院长：「还是不对，是微微握拳，然后掌心朝向身体内测，而不是后方」+「调研一下人类手掌手指关节，然后进行手部的精细建模」）
- **掌向量化实测**（raw 骨掌法向，世界系，模型面朝 -x）：左掌 (0,-0.17,-0.98)=恰朝大腿 ✓、右掌 (0,+0.17,-0.98)=朝外侧 ✗——**两手掌向相同未镜像**（四指蜷曲轴镜像不保证掌向镜像），常见机位下即「掌心朝后」

- **修复**：handPose v4 新增 **WRIST 表**（hand 骨绕局部 x：right supinate 180°=翻掌，双掌法向镜像对称均朝大腿；extend 15°=functional position 腕背伸）——掌心朝内+手背朝外+拇指朝前=真人垂手观感
- **精细建模**：HAND_POSE 表键=解剖关节（MCP/PIP/DIP），注释文档化【自然屈曲耦合比 PIP≈MCP×1.25/DIP≈MCP×0.55（Kapandji 抓握弧简化比，v3 值即落在比上）】【静息域 MCP20~40/PIP30~50/DIP10~25 取上沿】【拇指 CMC 对掌以内收+旋前近似】【腕 functional position】；来源=公认康复医学参照+本模型实测双源，**以院长对照真人验收为准**

## 2026-10-08（黑机 复验整改轮 BUG-103~105：小脑引擎三缺陷——位移补间清除范围、rest 懒捕获、批次冲突）

### BUG-103：`poseDriver.tweenPos` 按整骨清除补间——起立时"髋升起"被"髋前移"吞掉，腿伸而髋不升=脚穿地 0.38m

- **发现时间**：2026-10-08（黑机复验整改轮，实现院长③"起身不协调"的三段式配方时逐帧采样）
- **环境**：nono-poc `src/poseDriver.js` + `stand_up.json v3`（新增髋前移脉冲）
- **现象**：起立过程中髋高卡在坐姿高度不动（0.519 持续 1.2s），而腿部角度已按配方匀速伸直 → 足踝从 0.26 直落到 **−0.316（趾 −0.379）**——脚沉入地板 38cm；且髋高在 1.2s 后突然"追上"（说明补间不是没调度，是被清了）
- **根因**：`tweenPos(name, axis, …)` 内部调用 `this._dropTweens(name, { pos: true })`——`axis` 传 null 意味着**该骨所有轴的位移补间全清**。起立配方为"重心前移"加了 `translate hips z`，其调度时的清除动作把先前"髋 y 升"的补间一并删掉（两 op 同骨不同轴）；而 BUG-092 时代的配方都只有单轴位移，故该缺陷隐藏至今
- **修复**：清除范围收窄为"**骨 + 轴**"（`this._dropTweens(name, { axis, pos: true })`）；后由 BUG-105 进一步升级为"骨 + 轴 + 批次"
- **教训**：**"清除"的作用域必须与"写入"的作用域严格对称**——同骨多轴并行（髋 y 升 + z 前移）是自然的动作需求，引擎按骨清除等于禁止；补间类引擎的清除粒度应在设计时就写成"通道(channel)=骨×轴×（位移/旋转）"，而不是"骨"

### BUG-104：`poseDriver` 的 rest 为**懒捕获**——走路/坐姿中首次触摸的骨把"被摆过的姿态"记成静息（本轮①②③的共同根因）

- **发现时间**：2026-10-08（黑机复验整改轮，排查"坐姿腿角与实际设计不符"时发现）
- **环境**：`src/poseDriver.js`（`_bone()` 首次访问时 `rest: { x: node.rotation.x, ... }`）
- **现象**：把全部偏移清零（= 应为静息）后踝高是 **0.169** 而非静息值 **0.099**；同一组腿角数值在不同操作顺序下得到的坐姿差 12~16cm（床沿坐脚悬空 16cm / 椅坐 9cm / 有时又轻穿地）；院长复验见到的"坐着时手和腿穿模"即此偏差下的姿态
- **根因**：`PoseDriver` 只对 `hips/chest` 在构造时预注册，其余骨**首次被访时才捕获 rest**。首次访问通常发生在配方 `play()`→`tweenTo()`→`_bone(name)` 里——若此时骨架正被**走路 clip（mixer）/上一段坐姿**占用，捕获到的就是那一瞬的"被摆过的姿态"，被永久当作静息；此后所有 `apply()` 都以错误基准写回（rest+off），形成固定偏差。动作顺序不同 → 首次触摸时机不同 → 偏差不同，故表现为"时而悬空时而穿地"
- **修复**：构造时一次性注册全部人形骨（`DEFAULT_BONES` 22 骨 + 手型层 30 指骨），rest 必为真静息；实测修复后全零偏移踝高回到 0.099、起立结束精确回静息
- **教训**：**"基准/参考态"必须在系统进入可控状态的那一刻就锁定，不能懒加载到"第一次使用"**——懒捕获在"初始化即静息"的假设下才成立，而本项目在初始化后立刻会走进路/坐下（mixer 与配方交替接管骨架）。凡"记录当前值作为基准"的设计，都要问：**此刻的值一定是基准态吗？**

### BUG-105：同一次 `play()` 的后续 op 在**调度期**吞掉前面同频道补间——"脉冲两段式"永不生效

- **发现时间**：2026-10-08（黑机复验整改轮，起身前倾实测为 0mm 后逐条 dump `tweens` 定位）
- **环境**：`recipeExecutor.play()` → `_schedule()` 逐条调度；脉冲写法 = 同骨同轴两条 op（`deg:12` 无 delay + `deg:0, delay:0.25`）
- **现象**：配方里明明写了 `chest x 12°`（0→0.25s 再回 0），实测头部相对髋的前移量恒为 −26mm（毫无前倾）；dump `poseDriver.tweens` 见前倾补间**不在列表里**
- **根因**：`tweenTo/tweenPos` 在**调度时**（不是启动时）就执行清除，而"第二段 op（delay 0.25）"与"第一段 op（delay 0）"同骨同轴 → 第二段一调度就把第一段删了；第一段的 `t0 == now`（BUG-103 修复版按"未启动"判断时边界相等仍被删）
- **修复**：引入**补间批次**——`recipeExecutor.play()` 前 `driver.beginBatch()` 递增批次号；清除只清"同骨同轴**且不同批次**"的补间 → 同一次 play 内的多条 op 共存（按推入顺序逐帧覆盖=后段接管前段，脉冲成立），跨批次（新配方/打断）仍互清（旧振荡器不会复活）
- **教训**：**"声明"与"生效"要分清**——配方是"声明式序列"，同频道多条声明必须允许共存（后声明在时间轴后段接管），引擎不能在调度期做时间轴外的裁决；**脉冲式运动（去了再回）在动作库里很常见**（前倾预备、摆臂助力、呼吸式起伏），引擎必须原生支持

### BUG-100：步态 clip 起步/收势硬切跳变——首帧足部瞬移 0.28m、末帧"定格→立正"

- **发现时间**：2026-10-08（黑机步态轮，浏览器实测 `?room=1&model=v7` 行走全流程）
- **环境**：nono-poc（three.js 0.186 + @pixiv/three-vrm-animation 3.5.5），步态 clip `.vrma`（1.0s 循环）
- **现象**：走全流程 240 帧采样，足部世界位移出现两个尖峰——起步首帧 **0.28m**（单帧瞬移）、收势末帧约 0.012m 且姿态"卡在步幅中间→立正"硬切（观感为定格后瞬间换姿势）
- **根因**：两条路径都缺少"静息姿态 ↔ clip 姿态"的过渡：①起步 `action.reset().play()` 直接把骨骼从静息切到 clip 首帧（首帧=**触地姿**，双腿前后分开 ±0.24m）→ 一帧内瞬移；②收势先 `stopAllAction()` + 复位静息 → 从"步幅中间帧"直接跳立正
- **修复**：①起步 `action.fadeIn(0.18)`——three.js mixer 的权重淡入天然以"上一帧输出"为原始态，单 action 淡入即从当前静息平滑收敛到 clip；②收势 `settleWalkToRest(0.25s)`——捕获 clip 覆盖骨（21 骨）的当帧四元数/位移 → `stopAnimation` 复位并读取目标 → 用捕获值覆盖回去 → 渲染循环内 slerp 到目标（0.25s，覆盖式写入在配方/心跳之后、mixer 之前）
- **教训**：**mixer 的淡出≠回归静息**（fadeOut 的混合余量来自"上一帧自身输出"，单 action 下表现为原地冻结，不产生过渡）——需要"回到外部基准"的过渡只能显式做（捕获→复位读目标→slerp 回写）；另：**任何"播放源切换"都必须问一句"静息态与首末帧差多少"**，差得越多跳变越明显

### BUG-101：走速口径不一致（`WALK_SPEED` 1.05 vs 步态 clip 固有 0.88）——配方步态时代隐性，换真实足部接触即滑步

- **发现时间**：2026-10-08（黑机步态轮，接入 clip 前复核 `room.js` 常量）

### BUG-099：备料的 Krita Scripter 脚本（krita_handpaint_round1.py）首次实跑即崩——四个未验证假设一次性暴露

- **教训**：①**"备料"的完成定义 = 至少成功跑通一次**，不是文件写完——未实测的脚本必须在文档里显式标注"未验证"，不能让后续窗口误当可用资产；②**宿主环境的解释器能力必须先探针后写码**（依赖清单、API 是否存在都要实测，参考 BUG-097/090"探针先校准"同族）；③**日志要能活过异常**——先写盘再做事，别把证据和错误一起丢；④**字节透明≠语义透明**：底层读写全等不代表约定正确，跨库传递像素必须以"渲染/导出结果"为判据

### BUG-092：坐下/起立全程脚穿地板——髋部平移与腿部弯曲无运动学耦合，过程最低穿地 0.142m（院长复验问题④）

- **发现时间**：2026-10-07（院长白盒 v3 复验问题清单："起立的动作也有问题，过程都会穿模到地板下去"）
- **环境**：nono-poc `?model=v7&room=1`，sit_chair/stand_up/sit_bed 配方 v1
- **根因**：v1 配方的髋部 translate 与腿部 rotate/bend 是**独立补间+错峰延迟**（坐下=髋先降 0.6s、腿 0.15s 后才弯；起立=腿 0.55s 先伸直、髋 0.7s 慢慢升）——但髋骨骼是全身根位移，腿伸直时腿长恢复全文链长，**低位的髋+伸直的腿=脚必然插进地板**。探针实测：起立过程脚趾最低 **-0.142m**（t≈0.32s），床沿坐过程 **-0.158m**。本质：髋高被腿部角度唯一决定（踝贴地约束下 hip = 踝 + L1·cosα + L2·cos(γ−α)），任何偏离该曲线的髋轨迹都是穿地/悬空
- **修复（运动学耦合，数学上不可能穿地）**：腿匀速弯（α=90t，easing linear）时髋高按 **1−cos(α)** 走——easeInSine 的原函数恰为 1−cos(πt/2)、easeOutSine（sin(πt/2)=1−cos(90(1−t))）为其时间反演，故**坐下髋用 easeInSine、起立髋用 easeOutSine、腿一律 linear、同时长同起点（0.7s、废除全部 delay）**；该方案下踝点全程在站立/落座两端点间**单调插值**（ankle(t)=ankle_end+(ankle_stand−ankle_end)·cosα），对任意腿长/任意坐深成立。poseDriver 新增 easeInSine/easeOutSine 缓动；三配方升级 v2
- **验证**：骨骼探针 80ms 采样全程轨迹——坐下脚趾最低 **0.035**、起立最低 **0.034**、床沿坐最低 **0.023**（修复前 -0.14/-0.16），roomCheck 四姿态 0 违例

- **根因**：Chromium 对完全遮挡的窗口将 rAF 节流到 ~1fps（`document.hidden=false`、`visibilityState='visible'` 都不变——visibility API 只管标签页级，不管窗口遮挡级）。眨眼窗口仅 0.24s/3.6s 周期（6.7% 占空比），1fps 采样下单帧命中概率 6.7%，13 帧全 miss 概率 ~40%——**循环逻辑完好，是采样密度跟不上被节流的帧率**

- **修复**：非产品缺陷，无需修码。**采样方法学修正**：节流环境下验证"每帧逻辑"必须①用 monkey-patch 捕获调用实参（比读状态可靠）②采样窗覆盖 ≥10 个目标周期③或把目标值改为确定性触发（?blink=1）再验证
- **教训**：①**"循环死了"和"循环被节流"在遮挡环境下表现相同**——先测 rAF 实际频率再下结论；②价值状态（如眨眼脉冲）的低占空比特征会让短窗采样天然假阴性，验证逻辑要按"最坏帧率"设计；③此坑今天咬了两次（上午 PoC 冒烟测试 rAF 探针、深夜动作管线眨眼误报），同一根因，知识入档后不再重复排查

### BUG-085：sad/angry 表情眉毛中段被眼皮覆盖"截断"——表情形状键下压 13.6mm 沉入眼睑（院长现场定位并裁决上移补偿，修复）

- **环境**：nono-poc v7 贴片眼 / v6 3D 眼（两版皆有——表情形状键是同一套）
- **根因**（形状键 delta 实测）：`Fcl_ALL_Angry` 下眉毛顶点被下压 **13.4mm**（最深 -18.9mm）、`Fcl_ALL_Sorrow` 下压 **13.6mm**（全范围负值）——眉毛贴片沉入上眼睑区域，眼睑面覆盖眉毛中段=截断观感。**BUG-082 的前浮 1.5mm 远小于下压量，治不了；BUG-083 的 alpha 裁剪是贴图层，也治不了**（几何穿插只能几何解决）

### BUG-084：v6 眼球周期性穿出眼眶——driveEyes 静息基准钉死世界坐标，头部呼吸移动后失效（院长实测发现并锁定机制，修复）

- **发现时间**：2026-10-02 18:40 前后（院长在 v6·3D眼球版操作时发现：开心表情侧脸下眼球穿出眼眶，**周期性**出现；院长给出机制假设"呼吸让头部前后移动，眼球没有完全同步"——与实测完全吻合）
- **环境**：nono-poc `?model=v6`（3D 眼球总成版，眼部件为直挂 head 骨的独立 Object3D，由 main.js driveEyes 运行时驱动）
- **现象**：呼吸周期（4s）内眼球（虹膜/瞳孔/巩膜盘）相对眼眶周期性进出——头前移时眼球沉入/穿出眼眶边缘，头回位恢复；侧脸视角最明显
- **根因**（几何实测实锤）：driveEyes 的静息基准 restPos/ballC/nRest 全部是**加载时记录的固定世界坐标**，每帧用它们反推眼部件位置——呼吸 chest 旋转让头部 ±5mm 前后移动后，基准全部失效，眼部件被钉死在世界空间不跟头。实测：headZ ±5mm 摆动、irisZ **恒定 0.0566 纹丝不动**。对比 v7 贴片眼（VRoid 原生蒙皮）：头/眼睑/眉毛/眼球四组蒙皮顶点全部刚性同步——**穿模仅存在于 v6 运行时驱动路径**

### BUG-083：v7 仰视+视线向上出现"白块穿模"——眉毛贴图 alpha 长尾 × BLEND 模式 × 前浮组合效应（院长复验发现，两轮迭代修复）

- **发现时间**：2026-10-02 15:50（院长复验 v7 发截图：眉毛区域出现白块遮挡，"看起来像穿模"）
- **环境**：nono-poc（three 0.186 + three-vrm 3.5.5，MToon 渲染）
- **现象**：机位怼近+仰视+视线目标向上（鼠标在屏幕顶部）时，双眼上缘眉眼之间出现**浅色不规则碎片状物**，遮挡眉毛下半，像穿模。默认脸/angry/sad 均复现；**平视或视线向下永不复现**。此前 AI 侧实测（平视截图）永远通过、院长侧复现——视角敏感是分歧根因
- **根因**（三层叠加，实验定位）：
  1. **眉毛贴图 alpha 长尾**：VRoid 眉毛贴图（_07，1024×256）alpha 从笔画向外长尾渐变——alpha 0.01~0.5 的雾状像素 4.1 万个，是不透明像素（1.48 万）的近 3 倍，RGB 为棕色
  2. **BLEND 渲染无截断**：three-vrm 下眉毛材质 `transparent=true / alphaTest=0 / depthWrite=false`——低 alpha 像素全部参与渲染
  3. **前浮放大**：v7 眉毛前浮 1.5mm 把整个贴片（含雾状区域）抬进刘海区域，仰视+视线向上时半透明棕叠深发=浅色碎片。v5 无前浮故永不复现
- **定位实验**：①v5 同条件对照→无白块（锁定 v7 修改引入）②射线诊断→白块像素命中 SKIN 材质（眉骨上方）③隐藏眉毛 mesh（`Face_(merged)_5.visible=false`）→白块消失（锁定眉毛贴片渲染）④Blender alpha 直方图→长尾实锤
- **修复**（`build_v7_texture.py` v4，2026-10-02 两轮迭代）：
  - v3 首版：眉毛贴图 alpha 全局重映射 `smoothstep(0.25, 0.5)`——白块消失，**但眉毛"断了一截"**（院长复验否决）：眉毛笔画的柔边体量（alpha 0.1~0.5 的像素在 BLEND 下贡献眉毛的连续观感）被一并裁掉，笔画内部毛流间隙透出=断截
  - **v4 定版：逐列裁剪**——白块肇事区只在"眉毛笔画**上方**的雾状带"（前浮后叠进刘海的那部分），笔画本体及柔边必须原样保留。逐列扫描：每列以 alpha>0.5 核心像素上缘为界，上缘+4px 以上置 0；无核心像素的列不裁（保住尾梢淡出段）。裁 754/1024 列，眉毛本体零损伤
- **验证**（v4）：强仰视+视线向上（院长截图同款角度）×{默认/angry}——白块消失、眉毛完整连续无断截；平视矩阵同步过
- **教训**：①"裁掉低 alpha 雾状"不能一刀切——BLEND 模式下低 alpha 像素既是白块来源也是眉毛观感的组成部分，**空间域（笔画上缘以上）比 alpha 域（阈值以下）区分更精准**；②修一层问题前先想清楚同一批像素还承担什么观感职责；③numpy 视图陷阱：`a = px[:,3].reshape(h,w)` 是视图，写回 px 后 a 同步变化，修改统计要用 `.copy()`
- **教训**：①"表情下出问题"的目击定性不一定可靠——触发条件可能是相机角度+视线方向，与表情无关；②VRoid 贴图的 alpha 长尾在贴脸时隐形（与皮肤同色），任何把贴片抬离皮肤表面的几何修改都会让长尾显形——动眉毛/睫毛这类 BLEND 贴片几何前，先查贴图 alpha 分布；③复现 AI 侧 vs 用户侧分歧时，优先扫「鼠标位置×相机角度」参数空间而不是反复看同一机位
