## 二、第一轮讨论（2026-09-23）：针对 Live2D 形式

**院长诉求**：了解项目现状，针对电子宠物模块的 Live2D 形式进行讨论。

**本轮动作**：两路联网核实（运行时/授权/模型市场/AI 建模进展 + 模型成本/替代管线）。

**关键发现**（落档调研 §5.5.1）：
1. `pixi-live2d-display` 事实性停更（最后提交 2023-12，不支持 PixiJS v8）→ 运行时改荐官方 CubismWebFramework（2026-04 发 R5，WebGL 直渲）
2. 模型成本下修：Q 版外包 250-980 元/只（原认知 2000-8000 元是 VTuber 精模行情）；官方免费模型 32 个可商用（需署名，Hiyori 禁改设计）；BOOTH 现成模型 25-225 元

4. 模型约 2MB，hit 命中区域点击、motion 触发、自动眨眼/口型全是标准能力
5. Spine 类方案维持跳过（Pro $379 + 运行时许可摩擦）

**当时的建议**：一期 A 档伪 Live2D 起步，C 档从"三期旗舰"下修为"二期可试水"，先做半天官方免费模型 PoC。

## 三、第二轮讨论：形态质变 + 七条裁决

**院长裁决原话要点**：
1. 立绘设计通过 Seedream 进行
2. 角色形象是可爱美少女，名称"诺诺"，内接现有 AI 管线（具体设计后续讨论）
3. 产品形态=网站一个模块展示电子宠物，**所有人可见，类似虚拟直播间**。用户发弹幕，诺诺能看到然后回复；半小时没人发新内容就打瞌睡或去书桌上看书
4. 要有场景搭配，**椅子要能坐，不是贴图**
5. 如果 web/服务器不支持，可做桌面端，黑机有 Unity，用用户自己系统性能
6. 要解决：记忆系统、功能边界、形象设计、动作表情设计、界面 UI、场景交互、AI 配置（初版用我们的 API key 供服务，安装包仅线下给朋友，后续可让用户配自己的 key）
7. 目前仅作讨论

**本轮关键认知**：参照系变了——从"每人养一只宠物"变成"全站共享一只 AI 看板娘直播间"。原个人养成线（per-user 数值/掉落/串门）失效；三层记忆、条件台词、Live2D 运行时结论仍有效。

**当时的架构判断**：
- Web 能撑：Live2D 渲染各浏览器本地 GPU，服务器零渲染负载；弹幕走 Colyseus；真正的挑战是回复调度器（攒 2-5 条弹幕/8-15 秒触发一次回复，而非每条调 LLM）
- 桌面端重新定位：不是降级方案，而是三期扩展；web 形态下 API key 天然不暴露
- 提出机位问题：固定机位半身（省一半建模量）vs 全屋可走动

## 四、第三轮讨论：零外包 + 可行性第一

**院长裁决原话要点**：
1. 不考虑任何外包，所有工作自己完成
2. 建模已足够能让 AI 辅助（比如 GPT6），院长也可在 AI 辅助下工作
3. 建模工具应该有免费版，要求调研
4. 要全身建模，实现真实场景设计
5. **优先级最高的是建模能否实现**
6. 诺诺在不同情况下的 LLM 处理（含临场处理）——不希望她是被程序安排的木偶，而是 **LLM 大脑调用程序执行动作和其他功能的独立自主个体**。这一点是核心，但不是首先处理的

**本轮动作**：两路深挖（免费工具参数边界 + AI 辅助实战/新手周期）。

**关键发现**（落档调研 §5.5.2）：
1. **Cubism FREE 数字上做不了全身美少女**：官方标准参数集本身 40 个（FREE 上限 30）；官方全身模型实测 73-132 参数 / 178-262 ArtMesh / 138-180 变形器，超限 2-5 倍；日本制作公司 FREE 实测原话"做到身体是不可能的"
2. **AI 辅助边界：拆层可交给 AI，绑定不能**——See-through（开源/4070 可跑）解决拆层补全；但网格绑定/变形器/物理/动作曲线 AI 零辅助（.moc3 闭源无 API；r/ClaudeAI 2026-09 问"谁真做成过"，无成功案例）
3. 零基础周期：全身 2-4 个月/100-200h；全身+走路 4-8 个月，走路循环社区无先例
4. PRO 路径：42 天试用（导出 moc3 永久有效）或 indie 订阅约 700 元/年
5. 利好：Live2D 动作=预制 motion 按指令播放，与"LLM 自主调用动作"理念兼容（动作库=工具集）

**当时的建议**：1-2 周半身 PoC 验学习曲线，通过后再开 PRO 窗口攻全身。

## 五、第四轮讨论：院长问"如果是 3D 呢"——路线转向

**本轮动作**：两路深挖（3D 制作/AI 辅助 + Web3D 渲染/场景/同步）。

**关键发现**（落档调研 §5.5.3 + Web3D 专题文档）：
1. **VRoid Studio 全免费**（pixiv，v2.14 月更中，个人/企业免版税商用）；VRM 开箱自带骨骼/18 表情/眨眼/五音素口型/头发物理——"绑定地狱"不存在
2. 零基础 1-2 周达可直播质量（vs Live2D 2-4 个月）
3. **Mixamo 免费千级动捕动画**：走路/坐姿/手势直接重定向，单个分钟级（vs Live2D 走路 4-8 个月无先例）；坐椅子=坐姿动画+道具对位常规工程
4. AI 图生 3D：辅助成立（混元 3D 20 次/天、Tripo/Meshy 免费额度、GPT-6 操作 Blender 有实战），全自动在动画衔接环节不可靠（有复现全灭案例）
5. Web 渲染 three.js r186 + three-vrm 3.5.5 + Colyseus 评级 A-：20 人本地 GPU 服务器零负载；MToon 卡通材质；两个待 PoC 点=低配帧率/端到端时延
6. Neuro-sama 2025-11 转 3D 已验证"AI 主播+3D"路径
7. Unity 桌面端三矛盾（共享/同步/key 不泄漏）均有解，代价仅分发摩擦

**路线建议转向**：Live2D → 3D VRoid 主干；一周 PoC（Seedream 设定图→VRoid 捏模→three.js 渲染+动画→低配实测）。

## 七、专题解答：为什么本地 GPU 能渲染，但有些服务必须用服务器？

**院长的问题**：为什么可以用用户本地 GPU 渲染，而我们有些服务却需要服务器资源？

**答案的核心：分清"画面是谁算出来的"和"世界状态是谁说了算的"。**

1. **渲染=纯视觉计算，天然适合本地**：3D 画面是把模型数据（几何/贴图）按摄像机位置算出一帧帧像素。这个计算只需要模型文件+本地显卡，且每台机器看到的画面只需算一份。浏览器打开 three.js 页面时，模型文件先下载到本地（5-20MB），之后每一帧都由本机 GPU 生成。20 个人看同一场景=20 台机器各算各的画面，互不相关，所以服务器完全不参与渲染。这跟本地打开一个游戏是同一个原理，只是模型从网页下载。

2. **那服务器必须做什么？——四件本地做不了的事**：
   - **状态权威**："诺诺现在在房间哪里、在干什么"必须有唯一答案，否则 20 个人屏幕上她动作不一致。服务器维护这份状态（Colyseus schema），每个人的本地客户端只负责"按服务器给的状态把画面演出来"
   - **实时同步**：弹幕、诺诺的动作切换要瞬间广播给所有人——走 WebSocket
   - **可信/保密计算**：AI 调用必须经过服务器，因为 API key 不能下发到客户端（网页代码/安装包都能被反编译提取）；记账、权限同理
   - **持久化**：记忆库、弹幕历史要存在所有人都能访问的地方

3. **类比**：这就是所有多人在线游戏的标准架构（如英雄联盟/CS）——你的游戏画面 100% 是本机显卡渲染的，但"你在哪、打中没打中、对面在哪"由服务器裁决。我们做的是同一个架构，只是画面从写实枪战换成了卡通房间。

4. **那有没有"必须用服务器 GPU 渲染"的服务？有——云游戏/云渲染**（如网易云游戏、GeForce Now）：那种场景是设备太弱（老电视/低配本）跑不动，才改成服务器装一排高档显卡算好画面，把视频流推给用户。代价是极高的服务器成本和网络带宽，按小时烧钱。我们的目标设备（朋友们的电脑/手机）跑得动 three.js，完全不需要走这条最贵的路。

5. **离线版的边界**（呼应院长第 3 点）：做成离线游戏时，"状态权威+持久化"就搬到本机（单机存档）；但"AI 大脑"要么用户自配 API key（直连 LLM 官方，不经我们服务器），要么纯本地小模型。共享直播间形态和离线版是两条产品线，共用美术资产与动作库，不共用后端。
