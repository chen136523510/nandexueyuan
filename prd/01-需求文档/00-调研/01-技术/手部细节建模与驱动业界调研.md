## 一、核心结论（先看这个）

1. **VRM→Blender 往返有已知的 SpringBone/BlendShape 风险，且是插件官方承认的未修复项**：VRM 1.0 导出时 SpringBone 未完全自动化（导出后可能不摆动）、BlendShape 数据可能丢失——但可规避（最新版插件 4.5+ 修复了 VRM0/1 BlendShape 处理 + 导出选项检查 + 手动 SpringBone 配置 + VRoid Hub 测试）。（来源：插件官方 GitHub issue #1191，见 §二）
2. **手部拓扑业界有成熟参考图集**（Polycount wiki Limb/Hand Topology），高/低模线框对照可直接作为黑机建模模板；游戏手部通识密度为低模数百~2000 tris、特写级数千 tris（通识参考值，未交叉验证）。
3. **手指骨骼标准（每指 3 关节、双手 30 指骨）即业界通用配置**，特写驱动够用——精细度的差距主要在**网格与贴图**（指节形态/指甲/关节褶皱），不是骨骼。
4. **手部交互（按压/抓取）业界两大方案**：骨骼驱动指尖接触判定（我们现有 roomCheck 同款思路）与 attach-to-bone 吸附式抓取（VR 社区标准做法）——按压开关用前者即可，无需物理抓取。
5. **矫正形态键（corrective blendshape）是特写手部的业界标准配套**（防握拳指节穿插）——运行时驱动可直接设 morphTargetInfluences（three.js 标准能力），不依赖 VRM expressions 体系。

## 二、VRM→Blender 往返的已知风险与规避（风险 1，黑机执行）

**来源（一手）**：VRM-Addon-for-Blender 官方仓库 issue #1191（saturday06/VRM-Addon-for-Blender），开发者确认：
- **SpringBone**：VRM 1.0 导出未完全自动化——导出后 SpringBone 可能不出现或不动；VRM 0.0 可能"僵硬"不摆。开发者原话："当前 UI 设计为从 VRM SpringBone 直接组装原始数据……计划引入 setup helper 并扩充文档"（截至 2026-10 查询，尚未完全落地）。
- **BlendShape**：导出管线在规范/插件版本不匹配时可能丢 BlendShape 数据（模型导出后表情"变平"）。
- **规避清单**（搜索摘要+官方 issue 交叉）：
  1. 使用最新版插件（Blender Extensions 的 VRM 插件 4.5+ 修复了 VRM0/1 BlendShape 处理与舍入问题）；
  2. 导出时确认"Export BlendShapes"启用；
  3. SpringBone 必要时手动配置（选头发/裙摆根骨用插件工具或按 vrm.dev 的 VRMSpringBone 指南）；
  4. 导出后先在 VRoid Hub playground 或本地 PoC 验证 SpringBone/BlendShape 行为再交付。

**对本项目的影响**：往返基线测试（导入→不改→导出→PoC 加载对比）**必须先行**，回归清单=头发裙摆摆动/表情 18 种/眨眼口型/碰撞球。若有回归，先升级插件或改用 fork（VRM-Addon-for-Blender-Beyond）评估，再开始手部编辑。**本风险归黑机**（院长 2026-10-09 分配）。

## 三、手部建模精度标准与拓扑参考

- **拓扑参考图集（一手，业界建模师作品）**：Polycount wiki 的 Limb Topology / Hand Topology 页收录 Ben Mathis 等知名角色建模师的**高模/低模手部线框对照**（含 normal map 烘焙效果、手部 rig 动图）——黑机建模时直接对照其布线（指节环线、虎口过渡、掌心走向）。
- **面数分档**（通识参考值，未交叉验证）：
  | 档位 | 手部密度 | 适用 |
  |---|---|---|
  | 低模（远景 NPC） | 数百 tris | 全景远景 |
  | 标准游戏角色 | 数百~2000 tris | 全景全身出境（诺诺直播间机位） |
  | 特写/近景角色 | 数千 tris（含指甲立体/指节褶皱） | 手部特写镜头 |
  诺诺当前全身 50976 面（VRoid 导出），手部细化到数千面在直播性能预算内（本地渲染，无带宽约束）。
- **二次元画风注意**（院长定调：参照二次元手部绘画参考，真实人手复刻进本画风很别扭）：Blender 雕塑时以二次元手部绘画参考（简洁指节流线、抑制写实肌理）为形态基准，细节（指甲/关节色）交给 Krita 贴图层而非几何浮雕——几何只做大的形态（指节锥度、掌弓），写实微细节全部贴图化。

## 四、手部驱动与交互的业界方案

- **驱动层级**：业界标准=指骨 FK（每指 3 关节直接旋转）+ **姿态库**（grasp/grip presets：握拳/张开/指向等预设姿态参数化混合）+ 特写级加 **corrective blendshape**（握拳时指节皮肤互不穿插的矫正形）。我们的 handPose 层（HAND_POSE 参数表+耦合比）即"姿态库"思路的轻量实现 ✓ 方向正确。
- **corrective blendshape 的驱动路径**（特写预留）：**运行时直接设 `mesh.morphTargetInfluences[i]`**（three.js 标准能力，morphTarget 由 VRM 的 shape key 自动生成）——不依赖 VRM expressions 体系，代码可控、零额外管线。Blender 建模时预留 2~3 个矫正 shape key（握拳修正/伸指修正）即可。
- **手部交互（按压/抓取）**：
  - **按压类**（按开关/键盘）：骨骼驱动指尖移动 + **指尖骨点 vs 目标的距离/射线判定**（与我们 roomCheck 检测逻辑同款）+ 被按物的微动反馈。无需物理引擎。
  - **抓取类**（拿杯子/翻书）：VR 社区标准做法=**attach-to-bone 吸附**（物体父级切到手骨+偏移量预设，即"魔法吸附"），物理抓取（constraint+力反馈）仅高端 VR 需要。诺诺的抓取场景用吸附式即可，成本低表现稳。
  - 来源说明：本节为 VR/游戏开发社区通行做法的综合（未单一来源），关键机制（morphTargetInfluences/attach 模式）在 three.js/主流引擎文档中均为标准能力。

## 五、对项目的建议

1. **黑机施工规程**（手部精细化时）：①先跑往返基线测试（回归清单见 §二）②Blender 里只动手部 mesh 顶点/UV，不碰骨架结构与 SpringBone 分组③拓扑以 Polycount Hand Topology 图集为布线模板④形态基准=二次元绘画参考（院长供图），写实微细节全部走 Krita 贴图⑤导出后按回归清单复查。
2. **白机驱动层**（手部资产升级后）：HAND_POSE 参数表重新标定一轮（形态变了微调角度）+ 预留 morphTargetInfluences 矫正形接口（特写启用）。
3. **手部资产规格建议**（提前规划特写，院长定调"不接受推倒"）：手部区域细化到数千 tris + 指甲立体/指节褶皱走贴图 + 预留矫正 shape key 2~3 个 + UV 重排时不动脸部 island（保护已画的脸部贴图资产）。
4. **交互先行**：F1 关灯（程序示教：走到开关+握拳/伸指手型+抬手按压配方+指尖判定+灯反馈）不依赖手部资产升级，可先行验证交互链路。
