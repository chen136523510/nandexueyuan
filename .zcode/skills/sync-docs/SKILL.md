# Sync Docs - 项目文档同步器

你是一个严谨的项目文档同步专家。当用户要求"同步文档"时，你的任务是**回溯当前会话的所有代码改动和讨论内容**，将其准确同步到项目的核心文档中，确保文档与代码始终一致。

文档纪律规则定义在 `AGENTS.md` 的「文档与 Changelog 纪律」章节，本技能是其执行工具。

---

## 触发条件

当用户说以下任意一句时触发：
- "同步文档"
- "/sync-docs"
- "更新文档"
- "更新交接单"
- "同步 changelog"

---

## 强制工作流

### Step 1: 回溯改动

在 `<change_analysis>` 标签内执行：

1. **回溯当前会话所有代码改动**：检查 git diff、已编辑文件、讨论过的决策
2. **分类改动**：
   - 新功能（feat）
   - Bug 修复（fix）
   - 文档更新（docs）
   - 重构（refactor）
   - 架构变更（新增/删除目录层、技术栈变更、跨层重构）
3. **确认改动范围**：哪些文件被改了？改了什么？为什么改？

### Step 2: 确定要同步的文档

根据改动类型，按下表判断需要同步哪些文档（**只更新与本次改动相关的，不改无关内容**）：

| 改动类型 | 需同步的文档 | 路径 |
|---------|-------------|------|
| 新功能/需求 | 德塔 changelog + 需求池（如完成需求） + handoff | `prd/01-需求文档/04-德塔/changelog.md`、`pm/需求池.md`、`.ai/handoff.md` |
| Bug 修复 | 德塔 changelog + 德塔 bug-log | `prd/01-需求文档/04-德塔/changelog.md`、`prd/01-需求文档/04-德塔/bug-log.md` |
| 架构变更 | **根 CHANGELOG.md** + 德塔 changelog + handoff | `CHANGELOG.md`、`prd/01-需求文档/04-德塔/changelog.md`、`.ai/handoff.md` |
| 文件级变更 | **对应代码目录的 changelog.md** | 如 `src/api/changelog.md`、`server/src/routes/changelog.md` 等 |
| 里程碑状态变化 | ROADMAP + handoff | `pm/ROADMAP.md`、`.ai/handoff.md` |
| 设定/NPC变更 | 创作速查手册 | `prd/01-需求文档/04-德塔/02-设计/创作速查手册.md` |

**判断规则**：
- 架构级（新增/删除目录层、技术栈变更、跨层重构）→ 根 `CHANGELOG.md`
- 文件级（某目录内的代码改动）→ 该目录的 `changelog.md`（如果有的话）
- 模块级（德塔功能变更）→ `prd/01-需求文档/04-德塔/changelog.md`
- 师德墙模块的变更 → `prd/01-需求文档/06-师德墙/changelog.md`（不是德塔的）

### Step 3: 逐个更新文档

#### 3.1 根 CHANGELOG.md（架构级变更时更新）

**仅当发生架构变更时更新**（新增/删除目录层、技术栈变更、跨层重构）。格式：
```markdown
## YYYY-MM-DD 标题（版本号）

### 概要
一段话说明本次架构变更的内容和原因。

### 代码变更
| 文件 | 变更 |
|------|------|
| 路径 | 改了什么 |

### 决策依据
为什么做这个变更，替代方案是什么。
```
- 倒序排列（最新在最上方）
- 插入到 `---` 分隔线之后，第一条之前

#### 3.2 模块 changelog（德塔/师德墙等）

**格式规范**（严格遵循现有格式）：
```markdown
### [类型] 简要标题

- **时间**：YYYY-MM-DD
- **变更人**：陈梓键（{设备}）
- **背景**：为什么要做这个改动
- **变更内容**：
  1. 文件1 - 具体改了什么
  2. 文件2 - 具体改了什么
- **状态**：代码完成 / 已验证 / 待部署
- **关联文档**：xxx（如有）
```
- 倒序排列（最新在最上方）
- 插入到 `---` 分隔线之后，第一条之前

#### 3.3 代码目录 changelog（文件级变更时更新）

如果改动的代码目录下有 `changelog.md`（如 `src/api/changelog.md`、`server/src/routes/changelog.md`），且本次改动属于该目录的文件级变更，则在该 changelog 中追加一条记录。格式遵循该文件现有风格。

#### 3.4 Bug Log（仅当修复了 bug 时才更新）

**仅当本次修复了 bug 时才更新**。格式：
```markdown
### BUG-XX：简要描述

- **现象**：用户看到的问题
- **根因**：代码层面的根本原因
- **修复**：怎么改的
- **文件**：涉及哪些文件
- **状态**：已修复
```
- 编号接续现有最大编号（如当前最大 BUG-31，则新 bug 为 BUG-32）
- 倒序排列

#### 3.5 需求池（`pm/需求池.md`）

**仅当本次完成了需求池中的某个需求，或新增了需求时才更新**：
- 完成：将 `R-XXX` 从"待开发"表移到"已完成"表，补充完成日期和关联文档
- 新增：在"待开发"表添加新 `R-XXX`，分配编号（接续现有最大编号）

#### 3.6 ROADMAP（`pm/ROADMAP.md`）

**仅当里程碑状态变化时才更新**：
- 修改对应里程碑的标注（⛰️ uphill / ⛰️ downhill / ✅ done）
- 补充完成日期和产出物

#### 3.7 交接单（`.ai/handoff.md`）

更新交接单的关键部分：
- **最后更新**时间 + 设备 —— 时间精确到时分（`YYYY-MM-DD HH:MM` 本地时间），各「本轮产出」节标题同样精确到时分
- **稳定版本**：更新最新 commit 号（从 `git log --oneline -1` 获取）
- **当前阶段**：更新进度状态
- **本轮产出**：总结本次会话做了什么（代码变更、文件清单、验证结果）
- **下一步计划**：移除已完成项，补充新待办

#### 3.8 创作速查手册（设定/NPC 变更时更新）

**仅当本次涉及世界观设定、NPC、势力关系等变更时才更新**：
- `prd/01-需求文档/04-德塔/02-设计/创作速查手册.md`
- 更新 NPC 速查表、伏笔链、创作铁律等相关章节

### Step 4: 引用链检查

如果本次改动涉及**文件重命名或移动**，必须：
1. 用 `grep -rl "旧文件名" --include="*.md"` 搜索所有引用
2. 批量更新引用路径
3. 在同步清单中标注"引用链已更新"

### Step 5: 确认同步

输出同步清单，告诉用户哪些文档被更新了：
```
✅ 根 CHANGELOG.md - 新增 1 条架构级记录
✅ 德塔/changelog.md - 新增 1 条记录
✅ src/api/changelog.md - 新增 1 条文件级记录
⏭️ bug-log.md - 无需更新（本次无 bug 修复）
✅ 需求池.md - R-026/R-027 移至已完成
⏭️ ROADMAP.md - 无需更新（无里程碑变化）
✅ handoff.md - 更新本轮产出 + commit 号
⏭️ 创作速查手册 - 无需更新（无设定变更）
✅ 引用链 - 3 个文件的路径引用已更新
```

## 边界约束

| 约束 | 要求 |
|------|------|
| **只改相关部分** | 不改与本次改动无关的文档内容 |
| **保持格式一致** | 严格遵循现有文档的格式风格 |
| **倒序排列** | changelog 和 bug-log 最新在最上方 |
| **中文表达** | 所有文档内容用中文 |
| **不编造** | 只记录实际发生的改动，不推测 |
| **设备标识** | 根据会话上下文判断是"白机"还是"黑机" |
| **commit 号** | handoff 中的 commit 号从 `git log --oneline -1` 实际获取，不编造 |
| **路径准确** | 文件移动后引用链必须同步更新，不留断链 |
